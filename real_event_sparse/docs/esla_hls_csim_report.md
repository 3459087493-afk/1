# Q16-ESLA-K13 HLS C Simulation Report

## 1. Scope

This step implemented and tested the faithful φ(K)-scored Q16-ESLA-K13 HLS C model under:

```text
real_event_sparse/hls/q16_esla_k13/
```

Only Vitis HLS C simulation was used. No `csynth_design`, Vivado implementation, PYNQ execution, SSH connection, IP export, or bitstream generation was performed. Experiment 1 directories and `results/pynq_sparse_pareto` were not modified.

The complete 3444-sample test used the release-mode executable generated by Vitis `csim_design -O`. Because the execution environment limits a single process to about 30 seconds, the same executable and testbench were run over nine contiguous chunks (400 samples per chunk, final chunk 244), then aggregated. Every sample was evaluated exactly once; all nine chunks returned `CSIM_PASS`.

## 2. Configuration

| Parameter | Value |
|---|---:|
| Model | Q16-ESLA-K13 |
| Score | `mean(abs(phi(K_token)))` |
| Original sequence length | 16 |
| Active token count | 13 |
| Skipped token count | 3 |
| D_MODEL | 16 |
| ACTIVE_DIM | 16 |
| Fixed-point data | `ap_fixed<16,6>` |
| Accumulator | `ap_fixed<24,10>` |

`ACTIVE_DIM=16` is intentional. The validated Python Q16-ESLA-K13 candidate is token sparse but not Q16-S30 channel sparse. Setting `ACTIVE_DIM=11` would combine two different algorithms and would no longer reproduce `real_event_sparse/pytorch/esla_reference.py`.

## 3. Faithful φ(K)-K13 data flow

```mermaid
flowchart LR
    I[16 input tokens] --> IP[Dense input projection<br/>16 tokens]
    IP --> K[Dense K + phi(K) + score<br/>16 tokens]
    K --> TOP[Fixed top-13 selector]
    TOP --> IDX[active_token_indices 13]
    IP --> CX[Compact x_active 13×16]
    K --> CK[Compact/reuse phi_k_active 13×16]
    IDX --> CX
    IDX --> CK
    CX --> QV[Q/V generation<br/>13 tokens]
    CK --> ATT[KV, K_sum, attention<br/>13 tokens]
    QV --> ATT
    ATT --> POST[Output, LN, FFN<br/>13 tokens]
    POST --> POOL[Pool / 13]
    POOL --> CLS[2-class logits]
```

The HLS model computes full x and φ(K) once, selects top 13, copies selected entries into contiguous `x_active` and `phi_k_active` buffers, and reuses selected φ(K). K is not recomputed after selection.

| Stage | Source lines | Token bound |

These arrays are physically dimensioned by `ACTIVE_TOKEN_NUM` in the downstream path. There is no 16-token output tensor with inactive entries set to zero.

## 5. Loops that remain at 16

The following loops correctly remain dense:

| Stage | Source lines | Reason |
|---|---:|---|
| Input projection | 199-212 | φ(K) score cannot be computed before projected embedding exists |
| K projection, φ(K), score | 214-233 | Top-13 selection needs scores for all 16 candidates |
| Top-13 sorting/candidate scan | 35-75 | Selecting top 13 requires examining all 16 scores |

This first faithful version therefore proves post-K-selection token skipping. It does not claim that input projection or K projection was skipped.

## 6. Dense-mask audit

No fake dense-mask path exists in the ESLA core:

- no `selected[16]` or token mask is multiplied into dense output;
- no downstream `for token < SEQ_LEN` guarded by `if(active)` exists;
- the only `SEQ_LEN` loops in the kernel are the required dense input/K scoring front-end;
- downstream computation consumes compact buffers indexed from 0 to 12.

The top-K selector itself scans/sorts all 16 score candidates. That is selection overhead, not fake sparsity; its output is an explicit 13-entry list that controls physical compaction.

## 9. Can the design proceed to csynth?

**Yes, the C simulation gate is passed and the design is eligible for a separate csynth step.** The reasons are:

1. all 3444 samples completed;
2. prediction match vs Python reference is 99.42%;
3. accuracy/F1 are close to and slightly above the Python K13 values;
4. active-token selection agrees at 99.84% of index positions;
5. no NaN or Inf occurred;
6. static source audit confirms the intended downstream token loops are bounded by 13 rather than masked 16-token loops.

This report does not run or authorize csynth. Before any hardware claim, csynth must independently demonstrate:

- loop trip counts of 13 for Q/V, KV/K_sum, output, LN, FFN, and pooling;
- no II degradation that erases the reduced iteration count;
- actual RAM/ROM binding and memory access behavior;
- selector/compaction overhead;
- estimated total cycle reduction relative to a consistently synthesized dense Q16 baseline.

## 10. Claim boundary

At this point it is valid to state:

> Q16-ESLA-K13 has a faithful fixed-point HLS C implementation whose post-selection path physically processes 13 compact tokens and closely reproduces the Python reference in C simulation.

It is not yet valid to state:

- FPGA latency has decreased;
- BRAM traffic has been physically measured;
- csynth resources or cycles improved;
- the design has been implemented by Vivado;
- a bitstream exists;
- the design has run on PYNQ-Z2.
